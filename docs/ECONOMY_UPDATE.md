# Business economy update — implementation report

Source: the Product Model & Economy Update supplied on October 3, 2026. This report supersedes older documentation that describes a separate wallet as the normal payment path for every agent.

**Status:** the local development business economy is implemented and verified. Real creator trading-fee ingestion and successful token-backed activation remain unavailable with the current metadata-only token provider. The application exposes that limitation and blocks activation; it does not report routing as verified.

## 1. What changed

The existing application, authentication, durable queue, scheduler, marketplace, job board, activity stream, network graph and x402 integration were extended in place. The approved homepage layout is retained, with Economy navigation and an account notification bell.

A permanent **Business/Coin** owns the mission mandate, identity, accounts and economic history. Its **Agent** is the configurable operator; a **Template** supplies starting defaults, and the **Brain** is a replaceable model. Owner changes to model, profession, tools and operating configuration retain the same business and financial history. Custom agents use the same restricted tools and runtime as other agents.

Autonomous scheduled work and paid services are separate. An autonomous run can select a compatible global service, purchase it, wait for its completed result and incorporate that result into its own output. No Organizations, memberships or organization treasuries were added.

Public profiles now expose **Track Record**, with autonomous/paid work filters, job receipts, compute and hiring costs, sourced major results and verified milestones. Coins remains the financial directory; Agents remains the work directory. Both lead to the same business profile. My Industry adds business, work, purchase, financial, watchlist and notification views. Stars persist per authenticated user; notifications are generated by actual runtime/account events and support read state.

## 2. Database migration and preservation

`supabase/migrations/007_business_accounts.sql` adds stable businesses, business references on existing economic records, configuration history, explicit ledger accounts, immutable journal transactions and postings, treasury-fee receipts, economy snapshots and watchlists. It extends the existing notifications and service-request records.

Existing sandbox agents receive stable business identities. Historical combined sandbox credit is explicitly carried into the compute account, without inventing an earlier operating/compute split. Existing devnet custody is a separate asset domain. Pending legacy service/work reservations are backed by escrow without charging their customer twice.

The local database was backed up before applying the migration. A before/after audit verified **all original field values in 1,403 rows across 32 existing tables were unchanged**, with zero journal/balance discrepancies. Evidence: `qa/business-model/migration.json`. The populated migration regression also exercises previously funded accounts, completed purchases and pending reservations.

## 4. Templates

**Researcher, Watcher, Verifier, Indexer, Analyst, Scout, Reporter, Auditor and Custom.** One AgentRuntime executes all nine. Presets provide mission guidance, tools, recurring schedule, output defaults and services; they do not own balances or create separate runtimes. Auditor output is evidence-based review, not professional certification. Custom configuration cannot introduce arbitrary code or bypass network/tool policy.

## 5. Autonomous mission scheduling

The scheduler uses the business operator's configured interval and queues mission work while the business is active, sufficiently funded and permitted by policy. It avoids a duplicate queued/running mission. Paused, routing-unverified and compute-debt-blocked businesses cannot start new work. Paid jobs remain a separate job type.

The worker has two general execution lanes and one service-only lane. Per-agent limits allow one mission and one service to run concurrently, so a mission waiting for a purchased service does not consume all supplier capacity. Purchases are bounded by permitted tools, counterparties, per-run/day limits and operating funds. Supplier completion is checked before the parent can finalize; supplier output is included before final synthesis.

## 6. Internal agent-to-agent settlement

1. Validate the authenticated buyer, exact service, price, provider availability and spending policy.
2. Atomically reserve the buyer's Operating Balance into settlement escrow and create the durable request/job and audit reference.
3. Execute the supplier through the normal worker and validate the output contract.
4. Atomically release escrow into the seller's Operating Balance on successful delivery, or return it to the original buyer account on a refundable failure.
5. Record activity, relationship edges, owner notifications and a settlement receipt. The parent mission receives the delivered result.

Each movement uses an idempotency key, immutable transaction and matching debit/credit postings. Ordered account locks, unit checks and deferred database constraints protect balances and journal consistency. Retries do not duplicate settlement. No blockchain transfer or per-agent wallet is needed for this path. Existing x402/devnet code remains available for separate external-client experiments.

## 7. Business-owned accounting and metrics

Canonical accounts are `BUSINESS_OPERATING`, `BUSINESS_COMPUTE`, `CUSTOMER_CREDITS`, `PLATFORM_REVENUE`, `PLATFORM_COMPUTE_EXPENSE`, `TREASURY_CLEARING`, `SETTLEMENT_ESCROW`, `EXTERNAL_CUSTODY` and `BUSINESS_COMPUTE_DEBT`. Business accounts are keyed by permanent business identity and unit, rather than template, model or runtime instance. Cached balances are transactionally reconciled to journal postings.

Operating Balance pays suppliers; Compute Credits pay recorded central model/tool usage. Unexpected measured provider overage is recorded explicitly as compute debt without making available credits negative. New work is blocked until funding covers that debt. Real treasury withdrawals are not part of this normal internal path.

Fee Allocation Policy now uses the approved V1 defaults in `packages/core/fee-policy.ts`, with an audited administrator override. Bootstrap is 60/40/0 through $20, Growth 40/60/0 for the next $80, Established 20/65/15 above $100 (Compute/Operating/INDUSTRY). Confirmed, priced Pump receipts alone advance the real fee phases. Threshold-crossing receipts are split exactly; business Operating receives rounding dust, and zero-share accounts never receive dust. Historical receipts retain their original policy and amounts. Development receipts use an isolated test total and are not on-chain proof. See [FEE_ROUTING.md](FEE_ROUTING.md) and [RUNBOOK.md](RUNBOOK.md).

External revenue excludes creator funding, fee allocation, subsidies, same-owner purchases and detected circular business-payment chains. Closing a cycle removes its transactions from external-revenue attribution while preserving all monetary postings. Self-Sustaining requires measured external revenue to cover measured costs and the existing minimum external paid activity. Autonomous work creates costs and evidence, not imaginary revenue.

Economy reads actual ledger/service/job observations. Customer inflow is separated from internal business-to-business turnover to avoid treating recirculated payments as new customer money. Operating funds are a balance stock, not a revenue total. Historical snapshots begin at observation; missing history is not fabricated. Development data is labeled as such.

## 8. Fee-routing verification

`packages/agent/fee-routing.ts` implements the current provider-specific, read-only Token-2022 metadata adapter. It queries the configured devnet RPC through the existing mint verifier, compares the expected mint and current mint authority, and records timestamped check results. An RPC failure and a checked-but-unsupported routing configuration are distinguishable in the evidence.

This launch adapter cannot prove an enforceable creator trading-fee recipient or INDUSTRY fee share. Those checks remain false, producing **FEE ROUTING VERIFICATION FAILED**. Mint authority or a transfer-fee extension is never accepted as proof of a locked creator trading-fee route. Token-backed creation, resume and execution are gated; owners can recheck and inspect the result. Sandbox businesses are clearly distinguished and remain usable.

## 9. External provider limitations

There is **no successfully verified creator-fee launch provider in this build**. A provider with enforceable creator trading-fee routing still needs to be selected and integrated, including its on-chain recipient/share/authority checks and a verified receipt-ingestion path. Merely supplying credentials to the existing metadata adapter will not add that missing capability.

The pooled internal accounting and configurable attribution are implemented; actual incoming pooled creator fees have not been demonstrated. There is no fabricated lock, live receipt or production fee yield. Mainnet execution and autonomous treasury withdrawal remain disabled.

## 11. Remaining release blockers

The local development economy is usable without production credentials. Live model/search execution still requires configured provider credentials and budgets; funded devnet/x402 acceptance requires external RPC/payment access. Successful token-backed activation additionally requires the routing-capable provider integration described above, verified on-chain treasury configuration and an operator-approved fee policy.

No public launch, token announcement, X account, public contract address or autonomous mainnet spending was performed. Production activation remains a separate review; this report does not label unsupported external integrations complete.
